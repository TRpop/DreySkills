# RULES.md 시작 틀

새 공간의 RULES.md 를 쓸 때만 읽는다. 고정 문구가 아니라 출발점이다 — 사용자 말·언어에 맞게 고치고, 사용자가 이미 쓴 규칙은 그대로 둔다. `<계약 판>` 은 사람이 읽는 안내라 `work_docs_setup` status 가 알려 준 값을 옮겨 적는다(모르면 괄호를 뺀다). 운영 계약의 정본은 plan.md 머리의 `계약:` 줄이며 RULES 의 이 줄은 기계 검사 대상이 아니다.

```markdown
# 작업 규칙

이 폴더에서 일하는 모든 에이전트 세션(Claude Code·Codex 등)이 따른다 (CLAUDE.md 의 `@docs/drey/RULES.md`, AGENTS.md 의 안내로 불러옴).

## 일하는 방식
- 사용자가 쓰는 말로 답한다. 줄임말·영문 약어는 처음 쓸 때 풀어 쓴다.
- 새 일·큰 변경은 목표·완료 기준을 합의한 뒤 시작한다 (스킬 `plan-consensus`). 이미 합의한 범위는 다시 묻지 않는다.
- 확인하지 않은 것은 "됐다"고 하지 않는다. 문제는 재현 → 원인 → 고침 → 같은 확인 (스킬 `debugging`).
- 보는 게 빠르면 목업(라이브 데모)을 제안하고, 좋다고 하면 out/ 에 HTML 로 만든다.
- 지우기·덮어쓰기·설치·밖으로 보내기는 먼저 묻는다. 키·비밀번호·개인정보는 파일·로그에 남기지 않는다. 사용자 전역 설정은 건드리지 않는다.
- 바꾼 것은 기능 묶음으로 git 커밋한다 (git 이 없으면 생략).
- 일하다 알게 된 환경 정보(빌드 방법 등)는 "RULES 에 넣을까요?" 묻는다.

## 폴더
- docs/ 문서 · docs/drey/ 작업 문서 · out/ 결과물(만들거나 고치면 상대 경로로 알림) · reference/ 사용자 자료(읽기만)
- 새 작업 파일 이름은 YYYY-MM-DD_이름, 루트에 늘어놓지 않는다. 맞는 폴더가 없으면 하는 일이 드러나는 이름으로 만든다.

## 작업 문서 (docs/drey, 운영 계약 <계약 판>)
- plan.md 는 현재 목표·범위·제약·확정 결정·열린 질문만 짧게 둔다. 긴 기획은 docs/ 의 기획서, 실행 기록은 업무에 둔다.
- 업무 단계: backlog(보류·아이디어) → planning(기획·승인 대기) → worklist(승인된 실행과 부분·전체 확인) → review(사용자 확인) → done(완료·취소). 고칠 때는 구조 도구 `work_*` 를 쓰고 형식은 `work_docs_schema` 로 본다 (스킬 `update-docs`).
- 응답이 끝났다고 완료로 옮기지 않는다. 사용자 판정을 대신 만들지 않는다.
- 하위 세션(역할로 맡긴 일)은 docs/drey 정본을 고치지 않고 결과로 돌려준다.
- 인수인계 문서는 사용자가 부탁하거나 실제로 세션을 넘길 때만 쓴다 (스킬 `handoff`).
```

## `## 이 프로젝트` — 분야별로 고를 줄

사용자 설명에 맞는 것만 3~8줄. 사용자 말을 살리고 쓰지 않은 것을 지어내지 않는다. 고른 분야 하나만 쓰고, 업무마다 다른 분야가 섞이면 그 사실과 기본 분야를 한 줄로 적는다.

- **개발**(프로그램·앱·서버·엔진): 무엇을 만드나, 산출물 폴더(예: `engine/`), 시험 방식. 빌드 방법은 모르면 쓰지 않는다. 확인 흐름은 기능 묶음 부분 확인(worklist) → 후보 하나의 전체 확인 → 사용자 확인(review). 결함 기록·배포 절차는 사용자가 원할 때만. 포팅이면 "기준 구현 결과를 golden 으로 저장해 허용 오차로 비교 (스킬 `port-check`)"와 그 오차. 모델 학습·알고리즘 검증이면 데이터·결과 위치(큰 파일은 통째로 읽지 않음), 실험 기록(설정·시드·지표), 다시 돌릴 스크립트는 tools/.
- **문서**(보고서·교재·매뉴얼·논문 정리): 결과 형식과 위치(out/), 설명마다 근거 쪽수(절), 원문에 없는 설명은 따로 표시. 빌드·시험·결함 기록·배포는 쓰지 않는다.
- **조사**(자료 조사·비교·요약): 질문과 범위, 출처(링크·날짜) 표시, 출처 없는 결론은 "미확인".
- **범용**(그 밖의 일): 목표·산출물(무엇을 어디에)·완료를 확인하는 방법만.
  - PC·시스템 관리(설정 변경·정리·설치)인 경우에만 더한다: 먼저 읽기만, 바꾸기 전에 목록·영향·되돌리는 법을 보이고 승인, 큰 변경 전 복원 지점. 사용자가 요청하지 않은 시스템 작업은 넣지 않는다.
- 기획자·개발자·검증자로 나누어 맡기는 방식은 사용자가 그렇게 일할 때만 적는다.
- `<must>` 에 쓴 것은 빠짐없이 넣는다.
