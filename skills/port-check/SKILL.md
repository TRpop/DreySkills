# 포팅 결과 비교

기준 구현(예: Python 으로 검증한 알고리즘)의 결과를 정답(golden)으로 두고, 옮긴 구현(예: C++ 엔진)이 허용 오차 안에서 같은지 시험으로 확인한다. 언어는 상관없다.

## 1. 허용 오차
- RULES `## 이 프로젝트`·plan·기획서·업무 완료 기준에 적힌 지표·오차를 쓴다(예: PSNR 차 0.1dB 이내, 최대 절대 오차 1e-5, 픽셀 값 ±1).
- 없으면: 기획 세션이면 무엇으로 비교할지 사용자와 정해 plan 의 결정으로 적는다(스킬 `plan-consensus`). **하위 세션**은 사용자에게 묻거나 plan 을 고치지 않고, 쓸 수 있는 기준 후보와 함께 "허용 오차 미정"을 기획자에게 돌려준다(비교 숫자 표는 만들어 둘 수 있다).

## 2. golden 만들기
- 기준 구현을 그대로 돌려 결과를 저장하는 스크립트를 tools/ 에 둔다(예: `tools/make_golden.py`). 기준 구현은 고치지 않는다.
- 입력은 작은 것부터 여러 종류로: 보통 입력, 경계(0·최대값·빈 값·홀수 크기), 어려운 입력(노이즈 많음·큰 값). 난수가 있으면 시드를 고정한다.
- 결과는 다시 읽기 쉬운 형식(예: `.npy`·`.png`·raw + 크기 정보)으로 정해 둔 폴더(예: `tests/golden/`)에 저장하고 입력·설정·기준 구현 버전(커밋)·실행 환경을 같이 적는다. 큰 파일은 git 에 넣을지 먼저 묻는다(하위 세션은 기획자에게).
- 기준 버전·환경이 같으면 golden 을 다시 만들지 않고 재사용한다.

## 3. 비교 시험
- 옮긴 구현으로 같은 입력을 돌려 golden 과 비교하는 시험을 만든다(프로젝트 시험 틀 또는 tools/ 스크립트).
- 입력마다 지표(최대 오차·평균 오차·PSNR 등)를 표로 찍고 허용 오차를 넘으면 실패로 한다. 숫자를 보고 "됐다"고 한다.
- 속도 목표가 있으면(예: 1080p 30fps) 같은 시험에서 걸린 시간도 잰다(최적화 빌드, 여러 번 돌려 평균).
- 같은 코드·입력·환경에서 이미 통과한 비교는 다시 돌리지 않고 그 결과를 근거로 쓴다.

## 4. 어긋나면 좁히기
- 오차가 가장 큰 입력부터 본다. 입력을 더 작게 잘라 재현되는 가장 작은 경우를 찾는다.
- 단계별 중간 결과를 양쪽에서 저장해 처음 어긋나는 단계를 찾는다. 흔한 원인: 반올림·자료형(float/double, 정수 넘침), 경계 처리(padding), 색 순서·채널 배치, 인덱스 순서(행/열), 라이브러리 기본값 차이.
- 고칠 때는 스킬 `debugging` 순서를 따른다.
