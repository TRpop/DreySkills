# 손으로 고칠 때의 형식 (`drey-tasks/1`)

구조 도구도 `DreyBrowser.Mcp.exe --drey-docs` 명령도 없는 옛 앱이거나, 그 기능이 아직 없던 판(작업 공간에 `계약:` 줄도 없음)일 때만 읽는다. plan 에 `계약:` 줄이 있는 공간이면 이 형식으로 우회하지 말고 도구 상태(미확인이면 미확인)와 세션 재열기를 알린다. 도구가 있으면 허용 값은 `work_docs_schema` 가 정본이다. 고친 뒤 `DreyBrowser.Mcp.exe --drey-docs check .` 로 검사한다.

## 단계와 상태
| 파일 | 단계 | `- 상태:` 에 둘 수 있는 값 |
|---|---|---|
| backlog.md | `단계: backlog` | 아이디어 · 보류 (`- 재개 단계:` 와 재개 조건) |
| planning.md | `단계: planning` | 기획 중 · 승인 대기 (`- 확인 주체:`) |
| worklist.md | `단계: work` | 예정 · 진행 (`- 세부 단계:` 개발 대기·구현·부분 검증·통합 대기·전체 검증·재작업·배포 준비) |
| review.md | `단계: review` | 사용자 확인 대기 (`- 확인 주체:`) — 옛 기록의 코드 검토·시험 중은 읽기만 |
| done.md | `단계: done` | 완료 · 취소 (`#### 결과` 필수) |

`- 상태:` 에는 값만 둔다. 설명·기한은 `#### 상세` 에.

## 업무 하나
```markdown
### T-003 | 짧은 제목 (80자 이하)
- 유형: 기획|구현|유지보수|확인
- 상태: 예정
- 먼저: T-001, T-002   (없으면 없음)
- 요약: 한 줄 (120자 이하)
- 담당: 지금 담당 (80자 이하, 없으면 줄을 두지 않음)

#### 상세
무엇을·왜. 링크는 docs/drey/ 기준 상대 경로

#### 완료 기준
- [ ] 확인할 수 있는 기준
```

- 번호는 다섯 파일에 한 번만. 옮길 때는 원본에서 지우고 대상에 넣는다(번호·상세·기준 그대로, 상태만 대상 값으로).
- done 으로 옮길 때 `#### 결과` 에 날짜와 한 줄(취소면 `취소: 이유`). 새 업무는 `# 이전 기록` 위에 두고, 그 아래는 고치지 않는다.
- 목차(자동 목차 표시 사이)는 손으로 고치지 않는다. 어긋나면 `work_docs_index` 나 `--drey-docs index`.

## 사용자 확인 항목
review 로 옮길 때 `#### 사용자 확인` 에 `- [ ] UC-01 | 할 일과 기대 결과` 3~7개(필수가 아니면 끝에 `(선택)`), 메타데이터 `- 검토 회차: R-001` · `- 검토 대상: 버전 또는 커밋`. 수정본을 다시 보이면 회차를 올린다.

## 제출 정리 줄
전달받았거나 사용자가 요청한 제출만, 그 `##### RV-…` 기록 아래에 한 줄씩(`- 정리:` 만 필수). 제출 원문은 고치지 않는다.
- `- 정리: YYYY-MM-DD 무엇을 정리했는지` — 검토 내용 정리일 뿐 제품 수정 완료가 아니다(옛 `- 반영:` 은 읽기만).
- `- 확인됨: UC-01 · UC-02` — 저장된 사용자 결과로 확인된 항목만.
- `- 남은 확인: UC-03` — 없으면 `없음`.
- `- 후속 업무: DR-030` — 다섯 단계 파일에 있는 번호.
- `- 다음 행동: 사용자 확인|개발 대기|주 세션 정리 — 설명`
- 바로 정리할 수 없으면 `- 정리 대기: 이유`.

사용자가 대화로 결과를 알리면 `##### RV-001` 처럼 새 기록(`입력 경로: 대화(주 세션 기록)`)을 더한다. 판정을 대신 만들거나 자동으로 완료로 옮기지 않는다.
