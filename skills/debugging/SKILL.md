# 체계적 디버깅

> obra/superpowers 의 systematic-debugging 스킬(MIT, Jesse Vincent)을 쉬운 말로 줄여 옮김.

**원인을 확인하기 전에는 고치지 않는다.** 증상만 덮는 고침은 실패다. 쉬워 보이는 버그도, 급할 때도 같다.

## 먼저: 내 역할
- **고치는 쪽**(혼자 일하는 세션·개발자): 아래 1~4 를 따른다.
- **검증자**: 제품 코드를 고치지 않는다. 1 의 재현까지 하고, 실패를 한 보고서에 후보·환경·재현 방법·기대/실제·오류·로그 경로·영향으로 적어 기획자에게 돌려준다. 정상·승인된 예외·실패·미확인을 구분하고 부분 실행·누락·시간 초과를 통과로 세지 않는다.

## 1. 재현
- 오류 메시지·스택·줄 번호를 끝까지 읽는다. 최근에 바뀐 것(git diff·최근 커밋·설정)을 본다.
- **실패를 눈으로 확인한다.** 이미 실패하는 시험·검증자의 실패 기록·로그가 있으면 그것을 재현으로 쓴다. 없으면 프로젝트 시험 틀에 재현 시험을, 틀이 없으면 작은 스크립트를 만든다. 재현이 안 되면 추측하지 말고 자료(입력·환경·순서)를 더 모은다.
- 여러 단계를 거치는 일이면 단계마다 들어가고 나오는 값을 찍어 **어느 단계에서 깨지는지** 찾고, 잘못된 값이 처음 생긴 곳에서 고친다.

## 2. 비교
- 비슷한데 잘 되는 코드·예제·기준 구현을 찾아 다른 점을 모두 적는다. "이건 상관없겠지"라고 넘기지 않는다.

## 3. 가설과 확인
- "X 가 원인이다, 왜냐하면 Y" 하나만 세우고, 확인할 **가장 작은 변화** 하나만 해 본다.
- 틀렸으면 되돌리고 새 가설로. 고친 것 위에 또 고침을 쌓지 않는다. 모르면 "모르겠다"고 말한다.

## 4. 고침과 확인
- 원인에 대한 고침 **하나**. "하는 김에" 다른 개선을 섞지 않는다.
- **같은 재현**이 이제 통과하는지와 바꾼 부분에 닿는 시험만 돌린다. 전체 검증을 매번 다시 돌리지 않는다 — 전체 확인은 후보 하나에 한 번이고, 실패 뒤에는 영향 범위만 다시 본다. 확인하지 않은 것은 "됐다"고 하지 않는다.
- 다시 생길 수 있는 결함이면 재현 시험을 시험에 남긴다. 작업 중 바로 잡힌 작은 실수(오타·빌드 오류 등)에 별도 시험 파일·기록·인계 문서를 만들지 않는다.
- 기록: 프로젝트에 버그 기록이 있으면 증상·원인·고침·확인 방법을 짧게 남긴다(문서·조사 일에 개발용 기록을 강요하지 않는다). git 이면 기능 묶음으로 커밋한다.
- 작업 문서 단계 이동은 정본을 고치는 세션(기획자·혼자 일하는 세션)만 한다(스킬 `update-docs`). 하위 세션은 결과로 돌려준다.

## 세 번 실패하면 멈춘다
- 고침을 세 번 했는데도 안 되거나 고칠 때마다 다른 곳에서 새 문제가 나오면 구조가 잘못됐을 가능성이 크다. **네 번째 고침을 하지 말고** 확인한 것·가설·선택지를 알린다 — 혼자 일하는 중이면 사용자에게(planning 의 `승인 대기`), 하위 세션이면 결과로 기획자에게.
- 사용자 없이 시험을 돌리며 스스로 고치는 반복(자동 디버깅 루프)이 가능해 보이면 그렇게 할지 알린다.

## 이러면 잘못 가는 중
- "일단 X 를 바꿔 보고 되나 보자" · "아마 X 일 거야, 고치자" · "시험은 나중에, 눈으로 확인했어" · "여러 개 한꺼번에 고치고 돌려 보자" · "한 번만 더 고쳐 보자"(이미 두 번 넘게 실패) → 1번으로 돌아간다.
- 정말로 환경·타이밍·바깥 탓이면 조사한 것을 적고 알맞은 처리(다시 시도·시간 제한·오류 안내)를 더한다.
